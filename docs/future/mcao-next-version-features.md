## User direction

After the planned version is implemented and running, use **Oh My Pi (OMP)** as the agent harness for the orchestrator and its workers. Prefer OMP's RPC interface so the orchestrator can submit work, observe workers, send steering and follow-up messages, and cancel work. Transition away from other agent harnesses only during the later migration, with a plan for existing sessions and history.

OMP is the harness, not an AI model provider. The user still needs to select among model providers and models that the chosen OMP version and configured credentials actually support. Do not imply that a model, account, subscription, or feature is available merely because it appears in a mockup.

The earlier preference for Pi Durable is superseded by the user's OMP direction. Durable operation is still a requirement: investigate and prove OMP's actual persistence and recovery behavior. Do not assume that OMP uses Pi Durable or has equivalent checkpoint guarantees. The normal Pi CLI, the separate Pi Durable harness, and OMP are distinct integration choices.

## Deferred OMP migration work

- [ ] **Establish the baseline.** Wait for the current plan's accepted, running version. Inventory actual adapters, daemon contracts, versions, sessions, models/providers, permissions, packaging and platform evidence. Preserve existing task/session history and agree how active non-OMP sessions finish or migrate.
- [ ] **Prove OMP RPC.** Pin OMP and prototype locally on macOS and Windows. Verify process launch, protocol negotiation, request/response correlation, streamed event framing, prompt completion, live steering, queued follow-ups, cancellation, model selection, and handling of extension UI requests. Measure and bound event queues and output so a slow consumer cannot block workers.
- [ ] **Integrate behind MCAO's agent boundary.** Connect the daemon's scheduler and agent adapter to OMP without coupling UI components to OMP wire formats. Map capabilities and errors honestly. Confirm whether MCAO launches workers directly or delegates through OMP; retain a single authoritative view of workstreams, task state, worker identity, permissions and worktrees.
- [ ] **Establish durability and recovery.** Define ownership of MCAO task/approval/event state versus OMP session and pending-message state. Test UI disconnect/reopen, daemon restart, OMP process crash mid-turn, duplicate requests, dropped events, partial tool effects, and restart reconciliation before scheduling. Preserve histories and avoid duplicate external side effects. Recovery guarantees must be verified, not inferred from saved transcripts.
- [ ] **Preserve safety boundaries.** Keep task-owned worktrees, independent verification, explicit human approvals and authorized delivery. Map OMP tool permissions, extensions, skills, subprocesses and potential subagents to MCAO's policies. No worker may approve its own work or bypass protected operations; a worktree alone is not a security sandbox.
- [ ] **Plan cutover and rollback.** Pin and document executable/version, authentication, model/provider compatibility and supported operating systems. Introduce OMP on a controlled migration path; do not silently redirect or discard existing sessions. Disable other harness choices for new work only after proof, with a documented rollback and history-retention strategy.
- [ ] **Prove end to end.** Run real coordinator-plus-worker tasks through messaging, cancellation, failure and restart recovery, independent verification, human review and delivery on macOS and Windows. Test permission denial, unknown capability, version mismatch and missing credentials. Record exact versions and evidence.
