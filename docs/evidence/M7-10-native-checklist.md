# M7-10 native acceptance checklist

Run against one pinned candidate SHA on dedicated, non-production macOS and Windows environments. Use a test project and non-actionable message text; never use production credentials or data. Preserve each evidence artifact under a unique run directory and record the tested SHA, OS build, app build, daemon/runtime version, and result. These checks are deferred; do not run them in this worker pass.

1. **macOS — WKWebView target state and restart.** Launch the candidate app connected to the dedicated real daemon. Open `#/workspace`; select two project coordinators in turn, type a distinct unsent draft for each, and send a unique project note to each. Switch between targets and verify each log contains only that target's recorded note. Quit with Cmd+Q, relaunch, reopen `#/workspace`, and switch between both targets. **Expected:** the selected target and each unsent draft are restored; each daemon-backed transcript is still shown only under its own target. **Evidence:** `M7-10-macos-restart.png` and `M7-10-macos-restart.txt` (run ID, SHA, OS/app/daemon versions, selected target, draft/log observations).
2. **Windows — WebView2 target state and restart.** Repeat step 1 on Windows, quitting through the app menu or Alt+F4 and relaunching the candidate app. **Expected:** the selected target, per-target unsent drafts, and separate daemon-backed transcripts survive restart. **Evidence:** `M7-10-windows-restart.png` and `M7-10-windows-restart.txt` with the same identity fields.
3. **macOS — real daemon, project notes, Global, and model safety.** In the dedicated test project, send a unique benign message to its coordinator and confirm the daemon records it as a note, no reply is presented, and no task or approval is created. Select Global and send a unique benign message. Compare the UI with the daemon's recorded transcript: show a reply only if that reply is recorded; if the daemon reports `runtime_unavailable`, confirm the UI gives the runtime-unavailable status and no fabricated reply. Open Model settings, confirm non-launchable providers are disabled, and send a message after making a launchable local selection. **Expected:** the project message is a note-only operation; Global is live and truthful; model settings are task-submission-only and are not attached to conversation sends. **Evidence:** `M7-10-macos-live.png` and `M7-10-macos-live.txt` (safe message IDs, daemon transcript/request inspection, task/approval counts, menu observations).
4. **Windows — real daemon, project notes, Global, and model safety.** Repeat step 3 in the dedicated Windows test environment. **Expected:** the same note-only, daemon-backed Global, truthful runtime-unavailable, and non-launchable-provider behavior as step 3. **Evidence:** `M7-10-windows-live.png` and `M7-10-windows-live.txt` with daemon transcript/request inspection and task/approval counts.
5. **macOS — VoiceOver target picker.** Enable VoiceOver, focus “Choose conversation target,” open it with Return/Space, move to “Search conversations,” enter a query with no matches, and then use ArrowDown and the radio-list arrow keys to select a result; press Escape. **Expected:** VoiceOver announces the labelled search, the empty-result status, target names, selection, and returned focus; keyboard navigation never traps focus. **Evidence:** `M7-10-macos-voiceover.mov` and `M7-10-macos-voiceover.txt` (spoken output and key sequence).
6. **Windows — Narrator target picker.** Enable Narrator and repeat step 5 using Return/Space, ArrowDown, radio-list arrows, and Escape. **Expected:** Narrator announces the search, “No matching conversations,” target names, selection, and returned focus; keyboard navigation never traps focus. **Evidence:** `M7-10-windows-narrator.mp4` and `M7-10-windows-narrator.txt` (spoken output and key sequence).
7. **macOS — responsive layout and display scaling.** With the native app open to `#/workspace`, use Safari Web Inspector for the WKWebView to record `window.innerWidth`; resize the content viewport to exactly 961 CSS px and then 960 CSS px. Repeat at the macOS “More Space” and “Larger Text” display settings. **Expected:** at 961 px and above the activity column remains to the right of the main view; at 960 px and below it stacks above the main view; no horizontal clipping occurs at either display scale. **Evidence:** `M7-10-macos-layout-961.png`, `M7-10-macos-layout-960.png`, and `M7-10-macos-layout.txt` (viewport widths, scale settings, observations).
8. **Windows — responsive layout and DPI scaling.** With the native app open to `#/workspace`, use WebView2 DevTools to record `window.innerWidth`; resize the content viewport to exactly 961 CSS px and then 960 CSS px. Repeat at Windows display scaling of 100% and 150% (or the highest available scale). **Expected:** at 961 px and above the activity column remains to the right; at 960 px and below it stacks above the main view; no horizontal clipping occurs, and the breakpoint is measured in CSS pixels. **Evidence:** `M7-10-windows-layout-961.png`, `M7-10-windows-layout-960.png`, and `M7-10-windows-layout.txt` (viewport widths, scale settings, observations).
