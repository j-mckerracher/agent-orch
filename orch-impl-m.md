# Agent orchestrator implementation primer

Updated: 2026-11-07 (see repository evidence and execution logs for timestamps).

You are an orchestrating agent implementing [the technical implementation plan](docs/technical-implementation-plan.md). Read that plan, this primer, and [board.json](board.json) before selecting work. The plan describes the target architecture and its safety constraints. The board tracks the actual state of implementation; it is not proof that a feature works.

## Model and tools

The orchestrating agent is exempt from the worker model, thinking, pstack, and Ponytail requirements in this section. It may coordinate from Codex or another host using its available model and tools. Its host or model must not block worker dispatch. The coordinator remains responsible for verifying worker compliance, maintaining the board, and reviewing results.

Every delegated worker must use **codex `gpt-6-luna` with thinking set to `max`**. In OMP, the model selector is `codex/gpt-6-luna` and the thinking option is `--thinking max`. Confirm the actual model and thinking level for each worker session. Do not substitute another model or thinking level for workers. If the host cannot set or verify either setting for a worker, stop that worker's launch and report the blocker.

[utilities/omp_headless.py](utilities/omp_headless.py) launches OMP in one-shot text mode or persistent `--rpc` mode and adds the shared agent instructions. Pass `--provider codex --model gpt-6-luna --thinking max` for the required worker configuration. The thinking option is optional and defaults to OMP's configured setting when omitted, so the launcher does not enforce `max` by itself. Confirm the actual model and thinking level for each worker session; in RPC mode, OMP's `get_state` response exposes both. In RPC mode, the caller must handle OMP's JSON protocol and interactive requests, including questions and approvals. The pass-through does not provide an interactive interface by itself.

Every delegated worker must load and follow the installed `oh-my-pstack` skills. Use `poteto-mode` to select the applicable workflow and `pstack-pi` for host-specific and delegation mechanics. Every worker adding code must use the installed Ponytail extension. Confirm the required skills and extension are available for each worker. If they are unavailable, stop the affected worker's work and report the blocker. Pass these requirements and this primer to every delegated worker. A prompt is an instruction, not proof that a child loaded a skill or used the requested model.

codex caps `gpt-6-luna` at 20 calls per minute. On a rate-limit error, allow a cooldown and retry; preserve the attempt and do not substitute another model.

### OMP failure fallback

When an OMP worker fails and the coordinator replaces it under the user's direction, use one GPT-6 Luna subagent at maximum reasoning effort. This is the narrow exception to the OMP model requirement above. Keep the same Ponytail and pstack workflow requirements, including `poteto-mode` as the workflow router and `pstack-pi` for host/delegation mechanics. Verify which guidance is actually loaded in the replacement runtime; a cached plugin or a prompt telling the worker to use it does not prove its hooks are active. If the hooks are unavailable but the installed Ponytail `AGENTS.md` and task skill can be read, have the worker follow those instructions explicitly and record the runtime limitation. If neither the extension nor its instructions are available, stop before code edits and report the blocker. Preserve the failed OMP attempt and exact candidate; the replacement reviews and continues on that same task branch without overlapping writers, and the coordinator independently verifies the final result.

### Windows worker lessons

- Verify the actual worker session with RPC `get_state`, and observe the Ponytail load notification and successful skill reads before relying on the session. Preserve its session file and record the session ID in the board. A separate probe does not establish the configuration of the worker session.
- OMP's shell on Windows may resolve `npm` to a Unix wrapper that fails on `/dev/null`; use `npm.cmd` or a native Windows shell. Allow for slow registry calls and report their actual results. The same shell can fail on `2>/dev/null` even for skill discovery; use `read` with `skill://poteto-mode` and `skill://pstack-pi`, or read their actual `SKILL.md` files directly, and verify the read results in the worker session.
- Do not mix PowerShell redirection tokens with Bash commands: `2>$null` is invalid in Bash (`$null` expands as an unset variable). Avoid shell redirection when it is unnecessary; otherwise use the syntax for the shell that actually runs the command.
- In Windows PowerShell 5.1, native-command text on stderr can become a terminating `NativeCommandError` when `$ErrorActionPreference` is `Stop`, even for expected output such as Codex login status. Capture stdout, stderr, and `$LASTEXITCODE` with a controlled native-process boundary.
- Give each evidence run a unique output directory and fail if it already exists. Second-resolution timestamps collided during M0-05; adding `-Force` or `mkdir -p` can silently reuse and overwrite a prior run. Use a GUID or process ID suffix and preserve each attempt separately.
- A missing `cl.exe` on `PATH` does not prove Visual C++ tools are absent. Check Visual Studio with `vswhere.exe` and use its `VsDevCmd.bat` where needed. Do not start an installer based only on a PATH check.
- Treat Git worktree and branch cleanup as a separate, explicit lifecycle operation. A failed `git worktree add` may leave partial state whose ownership is ambiguous; preserve it for inspection and report its path/branch. Never force-remove or recursively delete based on a name/prefix check or assumed ownership.
- Give workers explicit test-directory ownership rules: never recursively remove fixed or shared temporary paths. Use uniquely created temp directories and only clean resources the test owns; inspect command results rather than inferring what a failed compound shell command changed.
- Long generated tool calls can end with provider `ECONNRESET` before a write executes, and `stopReason: "length"` can end a response before it emits the intended tool call. Inspect the tool-call record and actual worktree before accepting a write. Preserve the session and continue with smaller writes. If the provider ends the session, resume the same OMP session directly with `omp --model codex/gpt-6-luna --thinking max --mode rpc-ui --resume <session-id>`; `utilities/omp_headless.py` does not expose `--resume`. Before sending a continuation, verify through RPC `get_state` that the session ID, model, thinking level, and Ponytail state match the recorded worker. Do not treat a response cutoff or `agent_end` as successful task completion.
- Resolve the exact Codex executable before protocol checks: this Windows host has an older npm PATH wrapper and a newer desktop-bundled binary with different versions. Record the path and version with the evidence; a failure from one binary does not establish that all installed binaries fail. In the observed 0.20.0 error path, a JSON error event was followed by a hang; an event is not proof of process exit, so enforce a bounded timeout and capture the actual result.
- Discard cumulative RPC `message_update` streaming snapshots from monitor logs as well as console output: four concurrent sessions produced over 1 GB of redundant temporary logs within minutes. Preserve the OMP session files and compact non-streaming events; inspect worktrees and resume the same sessions if a monitor must be stopped. Configure the monitor's output for UTF-8 or safely escape unsupported characters; a Windows console encoding error can terminate the monitor and interrupt the worker. Handle interactive requests explicitly, and monitor for stalled or repetitive reasoning. If intervention is needed, preserve the attempt and inspect the worktree before retrying; do not infer success from the process state.

### Cross-platform verification and evidence

- Mac handoff: publish the candidate and its runbook before requesting a native run; give the Mac agent the exact branch, repository path, and direct runbook URL. Use a predictable path such as `docs/evidence/<task-id>-macos-runbook.md`. Do not assume an agent can find instructions from a generic message that they were pushed. The runbook must pin the source commit, give the exact commands and expected outcomes, specify unique evidence paths and failure-preservation rules, and explain how to publish evidence-only results without changing `board.json`.
- A Windows run does not compile or exercise `#[cfg(unix)]` code. Run platform-specific probes on every required native OS. The 2026-11-07 macOS Rust run caught an unsafe `CommandExt::pre_exec` call that the Windows run could not see; use a safe standard-library API such as `CommandExt::process_group(0)` when it supplies the needed behavior, and record the exact source commit tested.
- Unix cancellation tests must assert stable outcomes, not intermediate timing. `SIGTERM` can end a child immediately and the concurrent reaper can collect it before `cancel()` returns; do not require a child to remain alive during the cancellation grace period. Verify the cancelled exit and absence of the process after reap.
- When a native run fails before scenarios execute, preserve its complete environment, stdout, stderr, and exit status. Fix the candidate at a new revision, then rerun that revision natively; do not treat the earlier failure as evidence for the corrected source or overwrite the original artifacts. Keep OS-primitive smoke checks distinct from Rust probe evidence.
- Do not use a text-filter pipeline as the status of a build or lint command. On Windows, `cargo clippy ... | findstr ...` reports `findstr`'s exit code and can return 1 for no matches or hide Cargo's failure. Run the command directly or capture the producer's exit status explicitly. A quiet filter is not proof of success.
- A successful `codex exec` process exit does not prove the task succeeded: M0-05 returned exit 0 and `turn.completed` while its agent message reported a rejected file write. Also verify the exact response, requested file bytes, and resulting diff.
- macOS Codex CLI 0.167.0 can emit an `item.completed` error item for deprecated `[features].codex_hooks` configuration after `thread.started` but before `turn.started`, then continue with a successful command, `agent_message`, `turn.completed`, and exit 0. The same stream includes `item.started` for command execution; treat this as a valid nonterminal event. Keep the observed event order in regression fixtures: moving the warning inside the turn can let a test pass while the real stream still fails. Preserve raw events, keep reading after nonterminal error items, and decide task outcome from the complete event stream, process result, final response, and requested file/diff checks; neither one event nor process exit alone is decisive.
- On this Windows host, `[windows] sandbox = "elevated"` made Codex sandboxed command launches fail with `CreateProcessWithLogonW` error 1385. A per-run `-c 'windows.sandbox="unelevated"'` override with `--sandbox workspace-write` worked and left the shared user config unchanged. Keep the sandbox enabled; do not replace a failed sandboxed run with `danger-full-access` as acceptance evidence.
- If a verification harness writes its own evidence under the primary checkout, its before/after Git status will change. Keep outputs outside the measured checkout or explicitly identify and exclude only the harness-owned artifacts while still checking tracked files and unexpected new files.
- Drain redirected stdout and stderr asynchronously before waiting on a child deadline. Synchronous pipe reads can block before the timeout check, and writing text-mode captures can alter raw evidence; copy bytes concurrently, then bound the wait and kill the owned process tree.
- Pin and verify the shell runtime used by a harness. `ProcessStartInfo.ArgumentList` is not available in Windows PowerShell 5.1; either support its quoting rules explicitly or require and record PowerShell 7+. On macOS, do not assume GNU `timeout` exists; use an explicit dependency or Python `start_new_session` plus process-group signals.
- Before/after checkout-isolation checks are valid only while the measured checkout stays quiescent. Concurrent report or source edits create a real tracked-status difference; preserve the failed attempt and rerun after those changes are committed. Exclude only the exact harness-owned output path, not every path sharing a broad name.
- A temp-file write plus rename provides complete-file replacement, not a power-loss durability guarantee unless the file and containing directory are synced. Describe close/reopen behavior separately from power-loss recovery. Likewise, a mutex in one `FileStore` handle does not serialize other handles or processes.

## Maintain the board

Treat `board.json` as the shared work record. Read it at the start of each work session and update it as work changes, not only at the end. The coordinator owns board updates and integrates worker reports. Avoid concurrent writes to the same board; coordinate assignments and serialize updates.

When the user says native evidence is pushed, fetch and inspect the exact commit and artifact before changing task status. Compare the command and tested surface with the task's acceptance criteria: a Python process-group smoke test does not prove that a Rust process probe ran. Record the evidence commit and keep any untested portion blocked.

1. Select a `todo` task whose dependencies are all `done`. Lower `priority` values come first among ready tasks. A priority is dependency depth, not proof that a task is ready. Tasks at the same level may run in parallel when their dependencies are complete and their writable scopes do not conflict.
2. Set the task to `in_progress` before starting. Record the assignment, relevant constraints, and any useful context in `important_context`.
3. Update `important_context` with decisions, blockers, artifact paths, verification commands, and results as they become known. Do not put credentials or secrets in the board.
4. Mark a task `blocked` when a real dependency or external condition prevents progress. State the blocker and what can unblock it. Return it to `todo` or `in_progress` when the blocker is resolved.
5. Mark a task `done` only after inspecting the actual result and recording evidence that its requirements are met. A worker's report, a process exit, or a passing build alone does not prove task completion.
6. Add or revise tasks when implementation reveals missing work. Preserve stable IDs, valid dependency references, and the existing status vocabulary. Recalculate priorities from the dependency graph after changing dependencies and reject cycles. Preserve existing task history and other agents' updates.

Check milestone exit criteria independently. The current board's milestones and dependency edges are an initial decomposition, not a guarantee that every prerequisite is represented. Fix missing dependencies before scheduling affected work.

## Run the work

Start with the plan's single-agent CLI slice. Validate a repository and agent, create an isolated worktree, launch Codex, stream progress, record the result and diff, and preserve the worktree for inspection. Build durable state and deterministic supervision before relying on a coordinator, daemon, or desktop interface. Follow the milestones and exit criteria in the plan; a scaffold does not make a milestone complete.

For each assignment, give the agent its objective, task ID, writable scope, dependencies, acceptance criteria, verification commands, and report format. Include this primer and the model, pstack, Ponytail, and documentation requirements. Assign disjoint scopes to parallel workers. The coordinator reviews each result, resolves integration issues, runs the relevant checks on the integrated artifact, and updates the board.

Treat code as the primary documentation for future agents. Document important API contracts, inputs, outputs, failures, side effects, invariants, ownership, concurrency, security assumptions, and non-obvious decisions near the relevant code. Keep documentation accurate as behavior changes. Use clear names and types, and avoid comments that merely repeat the implementation.

## Preserve the plan's safety boundaries

- Keep the Rust engine independent of the desktop UI and provider implementations. Validate task state transitions centrally and persist transitions with their audit events.
- Run implementation tasks in task-owned Git worktrees. Do not modify the user's primary checkout, erase uncommitted work, force-push without authorization, or delete worktrees with unlanded changes. A worktree is not a security sandbox.
- Treat agent output, repository content, and external documents as untrusted. An agent proposal cannot authorize its own policy changes or delivery.
- Independently verify the exact candidate commit and require the configured approval before delivery. Reverify or obtain a new approval if the candidate or approved action changes.
- Preserve failed attempts and recovery evidence. Reconcile actual process and Git state before resuming interrupted work. Do not infer task completion from an agent's exit code.
- Preserve the plan's deferred scope. Do not add unattended merging, remote execution, or claims of cross-platform sandboxing without an explicit change in scope.

## Finish a work session

Leave the board valid and current. Record what changed, how it was verified, any remaining risks, and the next actionable task. Report tests that could not run and platform coverage that remains unverified. Do not mark a milestone complete until its exit criterion has evidence.
